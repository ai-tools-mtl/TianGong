# 专利交底书写作质量：术语翻译与语言水位

本技能与 `patent-de-ai` 互补：后者管"剔除 AI 味痕迹"，本技能管"术语怎么翻译、各章节该用什么语言风格"。两者配合，让交底书像资深专利工程师按章节规范手写。

## 〇、核心原则：专业 ≠ 过度学术，通俗 ≠ 过度口语

**交底书面向专利代理人（专利律师）。** 他们希望读到"专业平实"的文字——保留技术精确性，但不用 AI 套话、不用教科书定义堆砌，也不过度口语化。不同章节的"语言水位"不同，一刀切会出错。

## 一、语言水位三层模型

不同章节的语言要求不同，按以下标准调整：

| 层级 | 适用章节 | 标准 |
|------|---------|------|
| **专业平实** | 背景技术、现有技术缺点 | 场景驱动叙事，保留专业词汇，忌 AI 套话也忌口语 |
| **精准严谨** | 技术方案、技术领域 | 教科书级精确，完整定义，公式/符号引用规范 |
| **生动直白** | 缺点标题、效果标题 | 可适度口语化让代理人秒懂，但不轻浮 |

### 背景技术的特殊约束

背景技术面向非本领域代理人，须同时满足：
- ✅ **场景叙事**：从具体使用场景引入，建立画面感，让代理人知道"这个方案在解决什么具体问题"
- ✅ **专业平实**：用专业词汇但不用 AI 套话
- ❌ **不过度口语化**：不用"找个中间人""这玩意儿""干活"等
- ❌ **不跳过场景直接掉进文献分类**：遵循「场景 → 现有技术 → 缺点」三段结构

### 标题口语化的适用边界

"生动直白"水位（适度口语化的标题）**仅适用于缺点标题和效果标题**，让代理人一眼看懂痛点。**不适用于背景技术中的文献方向小标题**——后者须保留专业表述（如"凭证托管与委托协议""语义层权限控制"），不可口语化。

## 二、英文术语首次翻译铁律

**任何英文术语在正文中首次出现时，必须附带中文翻译，格式：`中文译名（English Term，缩写）`。** 后续可用缩写或中文。

不要假设代理人熟悉所有英文缩写——首现不译会制造阅读障碍，降低对交底书的信任。

### 分类翻译模板

**实体名称**：
- custodian → 凭证代管组件（custodian）
- Broker → 凭证代管方（Broker）
- Owner → 凭证所有者（Owner）
- Agent → 代理方/智能体（Agent）

**协议与方案**：
- SUDP → 安全无人委托协议（Secure Unattended Delegation Protocol，SUDP）
- 论文方案名（如 CapSeal）→ 保留原名，但需用一句话说明它是什么

**密码学/算法术语**：
- bilinear pairing → 双线性配对运算（bilinear pairing）
- DLP → 离散对数问题（Discrete Logarithm Problem，DLP）
- FHE → 全同态加密（Fully Homomorphic Encryption，FHE）
- TEE → 可信执行环境（Trusted Execution Environment，TEE）

**论文简称**（需解释含义）：
- BBS98 → Blaze、Bleumer 和 Strauss 于 1998 年提出的首批 PRE 构造（BBS98）
- AFGH → Ateniese、Fu、Green 和 Hohenberger 于 2006 年提出的单跳单向 PRE 构造（AFGH）

**工程术语**：
- ACL → 访问控制列表（Access Control List，ACL）
- API → 应用程序接口（Application Programming Interface，API）
- MCP → 模型上下文协议（Model Context Protocol，MCP）
- LLM → 大语言模型（Large Language Model，LLM）

### 翻译节奏

- 背景技术章节（代理人必读）：所有术语首次出现即翻译，宁可多译不可遗漏
- 技术方案章节：核心术语继续给出翻译，纯数学符号（如 `rk`、`sk_B`）可仅在符号表定义
- 首次给出翻译后，同节内后续可用英文缩写

## 三、效果边界精确表述

描述技术效果时，**精确表述方案的改善边界，既不夸大也不自贬**。这是审查员和代理人的常见关注点。

| 命题 | 正确性 | 处理 |
|------|:---:|------|
| 方案能完全消除某类攻击/问题 | ❌ 通常错 | 绝不在交底书中如此声称 |
| 方案对该问题完全无助 | ❌ 错 | 低估了方案价值 |
| **方案把风险/窗口从"永久"压缩到"瞬时"** | ✅ | 应如此表述改善边界 |
| 根治某问题需要多个机制协同 | ✅ | 点明协同关系，不独揽功劳 |

**原则**：用"压缩""收敛""降低"等可量化的边界表述，替代"消除""彻底""根治"等绝对化声称。若方案需要与其他机制协同才能达到最终效果，在背景技术末段点明，而非夸大单一方案的作用。

## 检查清单

- [ ] 各章节语言水位符合上表（背景专业平实、方案精准严谨、标题生动直白）
- [ ] 背景技术从场景切入，无过度口语残留
- [ ] 文献方向小标题保留专业表述，未口语化
- [ ] 所有英文术语首次出现有中文翻译
- [ ] 效果表述用了精确边界（压缩/收敛），无绝对化声称
